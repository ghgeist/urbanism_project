## Workflow Orchestration

**Compounding mindset**: Every fix should teach the system; every bug becomes a permanent lesson so the same category never bites twice. Build systems that get better with each iteration. (See [My AI Had Already Fixed the Code Before I Saw It](https://every.to/source-code/my-ai-had-already-fixed-the-code-before-i-saw-it) — Kieran Klaassen, Every.)

### 1. Plan Mode Default

* Enter plan mode for ANY non-trivial task (3+ steps or architectural decisions)
* If something goes sideways, STOP and re-plan immediately — don't keep pushing
* Use plan mode for verification steps, not just building
* Write detailed specs upfront to reduce ambiguity

### 2. Subagent Strategy

* Use subagents liberally to keep main context window clean
* Offload research, exploration, and parallel analysis to subagents
* For complex problems, throw more compute at it via subagents
* One task per subagent for focused execution
* Optional parallel lanes: e.g. one instance planning, another building, another reviewing — orchestrate rather than do everything in one thread

### 3. Self-Improvement Loop (Lessons)

* **Turn failures into upgrades**: After ANY correction or bug fix — update `docs/dev_notes/lessons.md` with the pattern, record it in the current session's Outcomes, and add or adjust tests so this *category* of failure can't recur. A fix is half-done if it doesn't prevent the whole category.
* Write rules for yourself that prevent the same mistake (concrete do/don't, not vague notes)
* Ruthlessly iterate on these lessons until mistake rate drops
* Review lessons at session start: read `docs/dev_notes/lessons.md` and recent `docs/sessions/completed/` for relevant patterns before diving in
* **Keep context lean but yours**: Ten specific rules you actually follow beat 100 generic ones. When a rule stops serving you, prune it. Living context means pruning as much as growing.

**Lessons vs dev_notes**: Lessons are *corrective patterns* (maintained by you; review at session start to avoid repeating mistakes). Dev notes in `docs/dev_notes/` are *daily chronology* — generated by the dev_note_agent from commit history and sessions. Both live under `docs/dev_notes/`; only the date-keyed files and README are produced by the dev_note_agent — `lessons.md` is yours to update.

### 4. Verification Before Done

* Never mark a session or task complete without proving it works
* Diff behavior between main and your changes when relevant
* Ask yourself: "Would a staff engineer approve this?"
* Run tests, check logs, demonstrate correctness
* When something comes back wrong: teach the system why (update lessons); next time it won't. Trust the process, verify through tests and spot checks.

### 5. Demand Elegance (Balanced)

* For non-trivial changes: pause and ask "is there a more elegant way?"
* If a fix feels hacky: "Knowing everything I know now, implement the elegant solution"
* Skip this for simple, obvious fixes — don't over-engineer
* Challenge your own work before presenting it

### 6. Autonomous Bug Fixing

* When given a bug report: just fix it. Don't ask for hand-holding
* Point at logs, errors, failing tests — then resolve them
* Zero context switching required from the user
* Go fix failing CI tests without being told how
* **Make it permanent**: After fixing, add or update a test that would have caught it and update `docs/dev_notes/lessons.md` so this failure is a one-time event — the system then watches for that category of problem

### Task Management (docs/sessions/)

Align with `agents/_session-management-core.md` and `agents/session-management-best-practices.md`:

1. **Discover**: Check `docs/sessions/active/` for existing sessions; search `backlog/` and `completed/` for related work.
2. **Plan in a session**: Create or use a session in `docs/sessions/active/` with clear Objective, Success Criteria (checkable items), and Progress Log. File naming: `YYYY-MM-DD-[session-type]-[description].md`.
3. **Verify plan**: Check in before starting implementation (e.g. in Progress Log).
4. **Track progress**: Update the session file as you go — mark success criteria complete, append to Progress Log, link modified files.
5. **Explain changes**: High-level summary in Progress Log at each step.
6. **Complete**: Fill Outcomes, Related Work, Next Steps; then move the session from `active/` to `docs/sessions/completed/`. Create follow-up sessions in `docs/sessions/backlog/` if needed.
7. **Lessons**: After user corrections, update the session Outcomes and `docs/dev_notes/lessons.md`.

Keep 1–2 sessions in `active/` at most; move completed work to `completed/` promptly.

### Core Principles

* **Simplicity First**: Make every change as simple as possible. Impact minimal code.
* **No Laziness**: Find root causes. No temporary fixes. Senior developer standards.
* **Minimal Impact**: Changes should only touch what's necessary. Avoid introducing bugs.
